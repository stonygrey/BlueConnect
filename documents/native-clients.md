# Native clients

This document describes the four native apps, `clients/swift`,
`clients/kotlin`, `clients/flutter`, and `clients/react-native`, which
drive the Verdigris device over BLE in Swift, Kotlin, Dart, and
TypeScript. Each one exercises its platform's implementation of
[Torann](https://github.com/stonygrey/torann) against the real
firmware, which is an independent implementation of the link protocol
in C. They are in this repository, and not in Torann's, because a
client is only correct relative to one version of
`proto/verdigris.proto`, the firmware, and the documents under
`documents/`, and because Torann's own rule is that its library code
does no I/O.

Each client covers Noise XX and IK with mutual key pinning, the button
ceremony, USB provisioning and enrollment from a scanned `SGNK1` or
`SGNE1` payload, the serial number, LED 1, and Echo commands, and the
soak loop. None of them implements client endorsements.

## Layout

Each client keeps the protocol code in a module with no platform
dependency, so that its tests run without a device, and puts the radio
backend and the screens in the app. The protocol module holds the
abstractions (`BleScanner`, `BlePeripheral`, `Advertisement`, the
options), `SegmentLink` and the shared `AdvertisementRegistry`, the
Noise `SecureLink` over Torann, and `VerdigrisPeripheral` over the
generated protobuf code.

| Client | Protocol module | App | Backend |
|---|---|---|---|
| `clients/swift` | `BlueConnect/Sources/BlueConnect` (SwiftPM) | `ZaffreSwift/` (SwiftUI, iOS and Mac Catalyst, generated by xcodegen) | `BlueConnect/Sources/BlueConnectCoreBluetooth` |
| `clients/kotlin` | `blueconnect/` (Gradle JVM module) | `app/` (Jetpack Compose) | `app/src/main/kotlin/com/stonygrey/zaffre/ble` (`BluetoothGatt`) |
| `clients/flutter` | `blueconnect/` (Flutter package) | `zaffre_flutter/` | `blueconnect/lib/src/ble` (the `universal_ble` plugin) |
| `clients/react-native` | `blueconnect/` (TypeScript package in an npm workspace) | `zaffre_rn/` (Expo, Expo Router) | `blueconnect/src/ble` (`react-native-ble-plx`) |

Each app follows its platform's own structure. The Swift app holds
`@Observable` model objects that SwiftUI views read through the
environment, with `AsyncStream` and actors in the library and no
Combine. The Kotlin app has Compose screens over `ViewModel` state
holders, a `data` package for the credential store and pairing
repository, and an `AppContainer` built by hand in the `Application`,
which is the layout Google's architecture guide gives. The Flutter app
has `ChangeNotifier` view models, repositories, and `provider` wiring,
which is the layout Flutter's architecture guide gives. The React
Native app is an Expo app with file-based routes under `app/` (Expo
Router: the scan list at `index`, the device's four tabs under
`device/`), plain classes for the repository, command runner, and soak
loop that notify React through `useSyncExternalStore`, and one
container built in `AppProvider` and read through context; the screens
under `src/ui` hold only their text inputs. In all four the
`SecureLink` is the initiator only. The responder is the firmware, and
the tests use Torann's own responder or, in the TypeScript package, a
fake Torann with the real message lengths.

## QR provisioning

Each pairing card has a Scan QR button for the two payloads
`lib/device` prints as QR codes: `SGNK1:<L|H>:<base64url 64 bytes>[:<NAME>]`
from `noise-provision low|high`, and `SGNE1:<base64url 64 bytes>[:<NAME>]`
from `noise-provision enroll`. An `SGNK1` payload on its own tier's card
replaces the tier's identity with the one from the QR and pins the
device key, with origin "provisioned", and sends nothing. An `SGNE1`
payload on the Low card opens one IK session as the enrollment key with
the device key pinned, sends `Enroll` with the low identity's public
key, and pins the device key with origin "enrolled"; the enrollment key
is never stored. A payload on the wrong card is refused. Unpairing a
provisioned tier also gives it a fresh identity, because the key from
the QR stays pinned and locked in the device's slot until `vg clear`
over USB or the button hold clears it.

The camera is the only platform piece. The Swift app uses AVFoundation's
metadata output, which works on iOS and on the Mac's camera under Mac
Catalyst with no dependency. The Kotlin app uses Google's code scanner
(`play-services-code-scanner` 16.1.0), which supplies the scanning UI
from Play services and needs no camera permission. The Flutter app uses
the `mobile_scanner` plugin (7.4.2). The React Native app uses
`expo-camera` (57.0.6), shown in a modal rather than a route so that the
scanned text returns to the card that opened it. The Swift, Flutter, and
React Native apps declare `NSCameraUsageDescription`.

Identities and pins are stored under the keys
`zaffre.link.identity.{low|high}`, `zaffre.pair.device.key.*`,
`zaffre.pair.device.name.*`, and `zaffre.pair.origin.*`: in the Keychain
on iOS, in `UserDefaults` on Mac Catalyst (a Keychain access group needs
a provisioning profile the local build does not have), in
`EncryptedSharedPreferences` on Android, in `flutter_secure_storage` on
Flutter, and in `expo-secure-store` (the Keychain on iOS) in the React
Native app. Each app logs `ZAFFRE-NOISE-PUB: <Low|High> <hex> cert=none.`
at startup, so that `lib/device` provisioning can find a key.

## Supported OS versions

The clients support the latest two iOS and macOS releases and the latest
four Android releases: iOS 26 and macOS 26 are the deployment targets,
and the Android apps declare `minSdk` 34 with `compileSdk` and
`targetSdk` 37; the React Native app sets the same floors through the
`expo-build-properties` plugin in `app.json`. The Android GATT code
therefore uses only the API 33 overloads, and the manifests carry only
`BLUETOOTH_SCAN` with `neverForLocation` and `BLUETOOTH_CONNECT`.

## Protobuf code

`lib/gen-proto` runs `protoc` over `proto/verdigris.proto` and writes
the Swift, Java and Kotlin (lite), Dart, and TypeScript code into the
four protocol modules, where it is checked in. `lib/gen-proto --check`
regenerates into a temporary folder and fails when the checked-in code
is stale. It needs `protoc` and `protoc-gen-swift` from Homebrew,
`protoc-gen-dart` from `dart pub global activate protoc_plugin`, and
`protoc-gen-es` (Protobuf-ES 2.16.0) from
`clients/react-native/node_modules`, which `npm install` in
`clients/react-native` provides.

## Torann

Every client takes Torann 0.3.1 from its platform's registry, so none
of them needs a checkout of Torann. `clients/swift/BlueConnect/Package.swift`
declares `https://github.com/stonygrey/torann.git` at exactly `0.3.1`,
which SwiftPM resolves to the repository's `v0.3.1` tag. The Kotlin
build resolves `com.stonygrey:torann:0.3.1` from Maven Central through
the `torann` entry in `clients/kotlin/gradle/libs.versions.toml`. The
two Flutter packages depend on `torann: 0.3.1` from pub.dev, and that
plugin's Android side resolves the same Maven Central artifact. The
React Native app depends on `@stonygrey/torann` `0.3.1` from npm, which
npm hoists into `clients/react-native/node_modules`; Metro bundles files
only from its watch folders, so `zaffre_rn/metro.config.js` adds the
workspace root, which holds the hoisted packages and the `blueconnect`
workspace package. A Torann release is a version bump in those four
places.

## Build, deploy, and test

Swift, on macOS with Xcode 27:

```bash
cd clients/swift/BlueConnect && swift test          # 43 tests, no device
cd clients/swift/ZaffreSwift
cp Signing.local.xcconfig.example Signing.local.xcconfig   # once; set DEVELOPMENT_TEAM
xcodegen generate                                   # writes ZaffreSwift.xcodeproj (gitignored)
xcodebuild -project ZaffreSwift.xcodeproj -scheme ZaffreSwift \
  -destination 'platform=macOS,variant=Mac Catalyst' -derivedDataPath build build
open build/Build/Products/Debug-maccatalyst/ZaffreSwift.app
```

The account-specific signing value, the team, is set in
`Signing.local.xcconfig`, gitignored and copied from
`Signing.local.xcconfig.example`, and `project.yml` applies that file to
every configuration of both targets. The signing style is `Automatic`
in `project.yml`, because it is not account specific: Xcode picks the
team's Apple Development certificate, and the Catalyst build needs no
provisioning profile because the entitlements are empty. `xcodegen
generate` warns and continues when the local file is missing, and the
build then fails at signing. `lib/zaffre.swift.app` runs the generate,
build, and `open` steps above, regenerating the project when
`project.yml` is newer, so it is the one command for the Catalyst
build. The first launch asks for the Bluetooth permission, and `open`
must be used rather than the bundle binary, for the reason given in
`build-deploy.md`.

An iPhone build needs a provisioning profile, which Xcode creates for
`com.stonygrey.zaffre.swift` on demand:

```bash
cd clients/swift/ZaffreSwift
xcodebuild -project ZaffreSwift.xcodeproj -scheme ZaffreSwift \
  -destination 'id=<udid>' -derivedDataPath build \
  -allowProvisioningUpdates -allowProvisioningDeviceRegistration build
xcrun devicectl device install app --device <udid> \
  build/Build/Products/Debug-iphoneos/ZaffreSwift.app
xcrun devicectl device process launch --device <udid> com.stonygrey.zaffre.swift
```

`xcrun devicectl list devices` prints the UDID of a phone that is paired
with the Mac, over USB or Wi-Fi. The two `-allowProvisioning` flags let
`xcodebuild` call Apple's developer services with the Apple ID signed in
under Xcode's Accounts settings, register the phone, and create the
profile. The call fails with `No Accounts` when no Apple ID is signed
in, and with `PLA Update available` until the team's Account Holder has
accepted the current Program License Agreement at developer.apple.com;
the agreement banner is shown only to the Account Holder, with that
team selected.

Kotlin, with the JDK that ships with Android Studio:

```bash
cd clients/kotlin
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
./gradlew :blueconnect:test                                   # 43 tests, no device
./gradlew :app:installDebug
adb shell pm grant com.stonygrey.zaffre.kotlin android.permission.BLUETOOTH_SCAN
adb shell pm grant com.stonygrey.zaffre.kotlin android.permission.BLUETOOTH_CONNECT
```

The Compose BOM is pinned to 2026.06.01 because Compose 1.12 requires
Android Gradle plugin 9.1, and the build keeps the AGP 8.13.2 and Kotlin
2.4.20 pins that Torann's Kotlin build uses on this machine.

Flutter, with the SDK at `~/development/flutter`:

```bash
cd clients/flutter/blueconnect && flutter test                    # 35 tests, no device
cd ../zaffre_flutter
cp ios/Flutter/Signing.local.xcconfig.example ios/Flutter/Signing.local.xcconfig   # once; set DEVELOPMENT_TEAM
flutter test integration_test/loopback_test.dart -d <device id>   # Torann on the device, no board
flutter run -d <device id>
```

`flutter test integration_test/...` installs a build whose entry point
is the test, and that build shows a blank screen when it is started from
the launcher. `flutter run`, or `flutter build apk --debug` followed by
`adb install -r build/app/outputs/flutter-apk/app-debug.apk`, replaces
it with the app. On the iPhone a debug build also closes as soon as it
is started from the home screen, because iOS 14 and later run a debug
Flutter app only under the Flutter tooling; `flutter build ios
--release` followed by `xcrun devicectl device install app --device
<udid> build/ios/iphoneos/Runner.app` installs a build that starts from
the home screen.

The iOS team is set in `ios/Flutter/Signing.local.xcconfig`, gitignored
and copied from `ios/Flutter/Signing.local.xcconfig.example`.
`Debug.xcconfig` and `Release.xcconfig` include it, and
`Runner.xcodeproj` names no team of its own, because a team chosen in
the Xcode Signing pane is written into the tracked project file and
overrides the xcconfig. The include is optional so that the simulator
build, which needs no team, works without the file.

React Native, with Node 26 and npm 11 from Homebrew and CocoaPods for
the iOS build:

```bash
cd clients/react-native && npm install                 # the workspace: both packages and @stonygrey/torann from npm
cd blueconnect && npx jest                             # 50 tests, no device
cd ../zaffre_rn
cp signing.local.json.example signing.local.json      # once; set appleTeamId
npx expo prebuild --platform ios                       # writes ios/ (gitignored) and runs pod install
npx expo run:ios --device <udid> --no-bundler          # builds, signs, installs; the phone must be unlocked
npx expo prebuild --platform android                   # writes android/ (gitignored)
npx expo run:android --no-bundler                      # builds and installs on the attached phone
npx expo start                                         # Metro, which the debug build loads from over Wi-Fi
```

`expo run:ios` and `expo run:android` build the `ios/` or `android/`
folder that exists, so a change to `app.json`, such as the version,
reaches the app only after `expo prebuild` has been run again for that
platform.

The debug build fetches its JavaScript from Metro on the Mac, so `expo
start` must be running while the app is used. With `CI` set in the
environment Metro does not watch the source tree, and the app receives
the bundle built at Metro's start until Metro is restarted. A release build
(`--configuration Release`) embeds the bundle and runs on its own, but
drops the console log that the hardware test method depends on.
`signing.local.json` is gitignored and holds the Apple team id,
`app.config.ts` reads it into `ios.appleTeamId`, and `expo prebuild`
writes that into the generated project as `DEVELOPMENT_TEAM`. `npm
install` pins every version exactly, and the workspace root
`package.json` carries `overrides` for `react` and `react-native`,
because the Torann package's peer dependencies would otherwise resolve
to a second, newer copy of each at the root.

`zaffre_rn/plugins/withSceneLifecycle.js` is a config plugin that makes
the generated iOS app adopt the UIScene lifecycle. UIKit in the iOS 27
SDK stops an app at launch when it has no scene manifest and no scene
delegate (the crash report names
`UIApplicationEvaluateRuntimeIssueForNoSceneLifecycleAdoption`), and the
app delegate `expo prebuild` writes for Expo SDK 57 creates its window
the old way, so without the plugin the app ends the moment it is opened
on a phone running iOS 27. The plugin writes the manifest into
Info.plist, writes `SceneDelegate.swift` next to the generated app
delegate and adds it to the target, and removes the window creation
from `AppDelegate.swift`, on every prebuild. It stops with an error when
the template's window creation block is not the one it expects, so a
later Expo template that adopts scenes itself stops the prebuild
instead of being patched a second time.

## Hardware test

Each app has a UI test that drives the whole Noise flow against the
board: select the device, pair High then Low, read and write the serial
number, read and toggle LED 1, Echo on High, Echo on Low (which the
device answers with `PERMISSION_DENIED`), three loop cycles, and
Unpair. The tests are
`clients/swift/ZaffreSwift/UITests/HardwareFlowTests.swift`,
`clients/kotlin/app/src/androidTest/kotlin/com/stonygrey/zaffre/HardwareFlowTest.kt`,
`clients/flutter/zaffre_flutter/integration_test/hardware_flow_test.dart`,
and `clients/react-native/zaffre_rn/uitests/Tests/HardwareFlowTests.swift`.
The React Native test is an XCUITest bundle with no host application.
It launches the installed app by bundle identifier, because the app's
Xcode project is generated by `expo prebuild` and nothing else edits
it. Its `testID` props are the accessibility identifiers the test
reads.

The pairing step needs the button on the board within 30 s, the
firmware's `PAIR_WINDOW_SECONDS`. Each client waits 40 s for the `Pair`
answer, so that the device's window closes before the client's wait
does.
`lib/device confirm` sends `vg confirm` over the USB shell, which the
firmware accepts as the matching button press for whichever tier is
armed, and answers `no pairing in progress` when none is. The test
runners cannot run that command themselves: a Mac Catalyst test bundle
has no `Process`, and an instrumented Android test has no access to the
Mac. The method that worked for all four clients is a loop on the host
that confirms about once a second for the length of the run, without
checking whether a window is armed, so that any window the app arms is
confirmed within a few seconds:

```bash
while true; do lib/device confirm 2>&1 | grep -E 'confirmed|Paired'; sleep 1; done
```

Each app also logs `ZAFFRE-PAIR: armed <tier>` the moment it sends
`Pair` (the unified log on Apple platforms, logcat with the `Zaffre`
tag on Android), which shows in a captured log where the ceremony
started. A watcher keyed on that line works for the Swift and Kotlin
apps; it does not for Flutter, because `flutter test` captures the
app's print output.

On Android, `flutter test` uninstalls the app after every run and
installs it fresh at the start of the next, which resets its runtime
permissions, and the permission dialog the app then shows blocks the
scan. Grant them from a second shell as the run installs the app:

```bash
while true; do
  adb shell pm list packages | grep -q 'package:com.stonygrey.zaffre.flutter$' && \
    adb shell pm grant com.stonygrey.zaffre.flutter android.permission.BLUETOOTH_SCAN && \
    adb shell pm grant com.stonygrey.zaffre.flutter android.permission.BLUETOOTH_CONNECT
  sleep 1
done
```

The Kotlin test grants its own permissions from `@BeforeClass` through
`UiAutomation`, and the Swift app keeps its Bluetooth grant on the Mac.

Then run the test. The Mac must be unlocked for the Swift run, because
the runner cannot bring the app forward on a locked screen:

```bash
# Swift: the first run asks to enable Xcode's UI automation mode (a system prompt
# from com.apple.dt.AutomationModeUI); the test cannot start until it is allowed.
xcodebuild -project ZaffreSwift.xcodeproj -scheme ZaffreSwift -destination 'platform=macOS,variant=Mac Catalyst' \
  -derivedDataPath build <signing settings as above> -only-testing:ZaffreSwiftUITests/HardwareFlowTests test
# Kotlin
./gradlew :app:connectedDebugAndroidTest
# Flutter
flutter test integration_test/hardware_flow_test.dart -d <device id>
# React Native: the app must be installed and Metro running (see above)
clients/react-native/zaffre_rn/uitests/run <device udid>
```

The provisioning flows have no automated test against the board,
because no test framework can hold a QR to a camera and the apps carry
no paste field. The payload parsers are unit tested, and the flows were
checked by hand by scanning the QR codes that
`lib/device noise-provision enroll` and `noise-provision high` print;
`lib/device clear all` unlocks the board afterwards.

One pinned client per tier means each app's pairing displaces the
previous client's pin on the board. `lib/device info` shows the pins
before and after, and `lib/device clear all` empties both slots, which
is also needed when the low slot was enrolled, because the firmware
rejects the ceremony for an enrolled slot.
